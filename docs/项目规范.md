# SolarEngine 项目规范

## 1. 目的与适用范围

本文定义 SolarEngine 一方源码的模块边界、构建流程、反射生成流程和托管互操作约束。它适用于 `Src/Engine`、`Src/BuildTool` 与 `Src/Applications`。

`Src/Libraries` 为第三方代码，不适用本文的命名、格式化和架构重构规则。升级或修改第三方库时，应保持上游目录结构与上游格式，并在变更说明中记录版本、补丁原因和回退方式。

本文与 [代码规范](代码规范.md) 配合使用。格式细节以仓库根目录的 `.clang-format` 和 `.editorconfig` 为唯一可执行来源；文档不复制或替代其配置。

## 2. 目录与所有权

| 目录 | 所有权与责任 | 允许的依赖方向 |
|---|---|---|
| `Src/Libraries` | 第三方依赖 | 不纳入引擎一方架构规则 |
| `Src/BuildTool` | Reflector、反射数据库、绑定和代码生成工具 | 可依赖必要的独立工具库；不得反向依赖 `Engine` 的 Runtime 或 Editor 实现 |
| `Src/Engine/Runtime` | 原生运行时、平台、内存、渲染、资源、类型系统及受控托管 Runtime | 可依赖一方基础库和受控第三方库；不得依赖 Editor 或 Applications |
| `Src/Engine/Editor` | 原生/托管编辑器、GUI、资源管理、视口与场景编辑 | 可依赖 Runtime；不得依赖 Applications |
| `Src/Applications` | 产品入口、启动和宿主程序集成 | 可依赖 Runtime 与启用的 Editor；不得承载可复用 Runtime 实现 |
| `Src/Engine/**/_Generated` | BuildTool/Reflector 输出 | 禁止手工修改；只能通过生成器、模板或反射输入更新 |
| `Src/Engine/_Ignore` | 非正式产品模块或保留实现 | 不得成为 Runtime、Editor 或 Applications 的新增生产依赖 |

依赖必须始终从上层流向下层：`Applications → Editor → Runtime`。`BuildTool` 是生成阶段工具，不是 Runtime 或 Editor 的运行时依赖。

## 3. 原生与托管边界

### 3.1 C++ 的职责

C++ 实现以下底层能力：渲染、平台、内存、线程、资源底座、反射核心、原生对象生命周期和性能关键路径。需要由 C# 使用的能力，应由 C++ 保持实现所有权，再通过稳定、受控的绑定或导出 API 暴露。

不得为方便 C# 调用而在 C# 中复制平台、内存、渲染或反射核心逻辑。

### 3.2 C# 的职责

C# 用于托管 Runtime 表面、Editor GUI、编辑器工作流和适合托管实现的脚本/工具逻辑。Runtime 与 Editor 托管项目分别由 `RuntimeCSharp.csproj`、`EditorCSharp.csproj` 构建，目标为 .NET 8。

C# 不得绕过绑定层直接假设 C++ 对象布局、所有权或地址稳定性。原生对象指针、句柄和生命周期必须通过既有的 `NativeInterop`、`Object.GetUnmanagedPtr` 或等价受控辅助 API 访问。

### 3.3 ABI 与互操作变更

以下变更必须作为一次完整的跨语言变更处理：原生类型布局、枚举值、函数签名、所有权约定、封送方式、对象指针访问方式、生成绑定模板。

此类变更至少要：

1. 修改 C++ 源接口或生成器输入；
2. 更新受影响的 C# 声明或生成模板；
3. 重新执行反射/绑定生成；
4. 构建受影响的 Runtime 和 Editor 托管项目；
5. 在变更说明中标明兼容性影响。

## 4. 反射与代码生成

反射元数据由 `Src/BuildTool` 管理。使用 `CLASS`、`REFLECTION_TYPE`、`REFLECTION_BODY` 等反射宏的一方头文件是生成输入；`_Generated` 下的 C++ 与 C# 文件是生成输出。

生成输出禁止直接修复。应按问题位置选择修改：

- 元数据不正确：修改反射宏、声明或属性；
- 绑定代码不正确：修改 BuildTool 的生成器、模板或转换规则；
- 生成时序不正确：修改 CMake 的预编译目标或目标元数据；
- C# 原生对象指针访问不正确：修改生成逻辑，统一使用受控对象指针辅助 API。

构建系统通过 `PRECOMPILE_PROJECT` 收集目标输入，并由 `PreCompileUpdate`、`PreCompileRebuild`、`PreCompileClear` 调用 SEBuildTool。修改反射输入、生成器或绑定模板后，必须运行适当的生成目标；不要依赖旧的 `_Generated` 文件通过构建。

## 5. 构建与配置

项目基线为 CMake 3.26+、C++17、Visual Studio 2022 x64 和 .NET 8。标准本地入口为：

```powershell
cmake --preset x64-Debug
cmake --build --preset Debug

cmake --preset x64-Release
cmake --build --preset Release
```

根 CMake 选项 `USE_EDITOR`、`USE_DEVELOPMENT`、`USE_PROFILER` 控制编译特性。新增功能必须使用现有选项或新增具名 CMake 选项，不得通过本地路径、未记录环境变量或临时宏改变默认产品行为。

新增 Runtime、Editor 或 Application 源文件时，应同时确认其所属模块的 `CMakeLists.txt`、托管项目包含规则和反射目标输入是否正确。新增资源与 Shader 时，应确认现有资源复制和 Shader 输出路径能够覆盖它们。

## 6. 变更准入

本项目当前不以 CI 或测试框架作为第一版规范的前置条件。每个变更仍应完成与风险相称的本地验证：

| 变更类型 | 最低验证 |
|---|---|
| 单纯 C++ 实现或头文件 | 受影响 CMake 配置的 Debug 构建；必要时 Release 构建 |
| Runtime/Editor C# | `dotnet build` 对应项目，并处理或记录现有基线失败 |
| CMake、目标依赖或资源复制 | 重新配置并构建受影响预设 |
| 反射、绑定、Interop | 重新生成，再构建 Runtime 与 Editor 的原生和托管目标 |
| 第三方库 | 按上游构建/验证方式执行，不混入一方格式化 |

格式化仅覆盖被修改的一方源码；不得为了满足格式化而批量重写无关文件。若当前基线已有不相关构建错误，变更说明应明确列出它们，不能将其伪装为本次验证通过。

## 7. 规范维护

新增稳定模块、生成路径或跨语言边界时，应同时更新本文。格式规则的修改优先落在 `.clang-format` 或 `.editorconfig`；本文只说明其适用范围和使用原则。
