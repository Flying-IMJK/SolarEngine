# SolarEngine 代码规范

## 1. 适用范围与规则来源

本规范适用于 `Src/Engine`、`Src/BuildTool`、`Src/Applications` 的一方 C++、C#、CMake 和生成器输入。只要求新增代码及实际修改范围遵守新规则；不因存量提示而批量格式化、重命名或设置构建门禁。`Src/Libraries`、`_Generated` 和其他第三方或生成代码不作人工规范化。

AI 与开发者应直接读取根目录的 `.clang-format`（C++ 排版）、`.clang-tidy`（C++ 可配置诊断）和 `.editorconfig`（C# 格式与命名）。本文只补充配置无法表达的语义、例外和适用边界。修改规则时先改对应配置，再检查本文有无冲突；同模块惯例仅在配置和本文均未覆盖时作为参考。

## 2. 通用约定

- 顶层命名空间为 `SE`，子命名空间按 `PascalCase` 命名；需要遵守既有 ABI、反射、绑定、序列化或外部接口契约的名称保持原样，并在修改处局部说明或抑制诊断。
- 一个文件应有明确的主要职责，但不强制“一文件一类型”。修改应留在所属模块，不能以跨模块引用绕过依赖方向。
- 新增公开 API 的英文注释应说明调用者必须知道的所有权、线程、失败行为或互操作契约；直观代码无需逐行解释。
- 沿用现有日志、断言、异常和平台抽象；平台实现放在既有 Platform 子层，由公共抽象调用。

## 3. C++ 补充规则

- 新头文件使用 `#pragma once`。所有新写或实际整理的 include 分组使用 `#include <...>`，路径从目标配置的模块 include 根目录解析，不用 `../`。若修改已有文件的某个 include 分组，将该分组整体统一为尖括号；其他文件和分组不批量处理。
- include 保留模块内既有分层，当前实现自己的头文件靠前，随后是 Core、Runtime、Editor、其他模块及第三方依赖。`.clang-format` 负责可实现的排序；尖括号的统一写法是人工及 AI 审查规则，不要求编辑器诊断。
- `using namespace` 仅可用于标准库和第三方库，包括头文件的全局作用域。新代码不为一方命名空间添加 `using namespace`；已有一方写法不因本规范批量修改。这一允许范围由人工及 AI 审查，不启用会一概禁止的现成检查。
- 类的可变静态字段使用 `s_PascalCase`；现有 clang-tidy 不区分类静态字段和实例字段，由 AI 与人工审查。原始指针参数使用 `p` 前缀；局部指针、成员指针、智能指针不因其类型额外加前缀。原始指针应遵守项目既有非拥有引用或受控地址约定，拥有关系使用项目现有对象、智能指针或容器设施。
- `auto` 可用于类型直观的初始化、模板、迭代器和 lambda 等场景；公开接口及所有权边界写明类型。
- 异步、任务及 GPU 交互应交代线程亲和性、提交与完成边界和资源存活要求。可恢复错误使用既有日志或结果路径；编程错误和不变量使用 `ENGINE_ASSERT`。不得把异常、系统错误码或平台资源泄漏到不负责处理它们的模块边界。

## 4. 反射、生成与原生绑定

- 反射宏只放在 BuildTool 可稳定解析的一方声明中；宏、属性和类型名变更视为绑定 API 变更。
- 不手工编辑 `_Generated`；修改生成输入、模板或 BuildTool 后，按变更类型验证新生成结果。
- 原生绑定、Box/Unbox、对象指针和封送行为变更应同时考虑 C++ 布局、生成逻辑和 C# 声明。
- 生成的 C# 获取脚本对象原生指针时使用 `Object.GetUnmanagedPtr` 或项目定义的等价受控 API，不直接读取内部指针字段。

## 5. C# 补充规则

- 禁止使用 `var`，包括普通局部变量、`out var`、`foreach (var ...)` 和 `using var`。匿名类型局部值改用具名类型或显式元组。`.editorconfig` 提示显式类型；它未覆盖的写法仍按本条审查。
- 返回 `Task` 或 `ValueTask` 的新异步方法以 `Async` 结尾；接口实现、重写方法和事件处理器遵守对应契约名称。
- 不新增 `global using`。单表达式的简短属性、访问器和方法可以用 `=>`，其余遵守 `.editorconfig`。
- Runtime 和 Editor 的新增托管 API 不得使用可空引用类型标注，也不得启用 Nullable 注解或警告。允许 `int?` 等可空值类型及对应的 `Nullable<T>`。`unsafe`、`LibraryImport`、自定义封送和 `NativeInterop` 调用应集中在 API 边界，说明原生所有权、缓冲区大小、线程要求和失败行为；不得缓存无生命周期保证的原生指针或自行复制原生对象布局。
- GUI 控件遵循 Control/ContainerControl 的事件与布局契约；重写输入回调时，除非有明确理由，不吞掉基类需要处理的事件。Editor 功能依赖 Runtime 的公开托管表面。

## 6. CMake 与依赖

- 新源文件通过所属模块现有的 `RUNTIME_ADD`、`EDITOR_ADD` 或等价机制登记。新目标声明所需 include 根和最小可见性依赖，不在 include 中以 `../` 绕过目标依赖。
- Runtime 不依赖 Editor，Editor 不依赖 Applications，BuildTool 不依赖 Runtime/Editor 的实现。CMake 不写入开发者机器绝对路径、临时生成目录或未记录的环境假设。
- C# 构建沿用根 CMake 的 `CSHARP_TARGET`。参与反射的模块使用 `PRECOMPILE_PROJECT`，将可解析头文件作为生成输入。

## 7. 变更检查

按变更类型执行[项目规范](项目规范.md)的适用验证，并分别记录配置解析、静态诊断、生成结果、编译和运行结果；未执行的步骤明确注明。检查提交范围不包含第三方或生成文件的意外人工改动，且不引入反向模块依赖。
