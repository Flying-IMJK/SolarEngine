# SolarEngine 代码规范

## 1. 适用范围与优先级

本规范适用于 `Src/Engine`、`Src/BuildTool` 和 `Src/Applications` 的一方 C++、C#、CMake 及相关生成器代码。`Src/Libraries` 保持第三方上游规范，不进行一方格式化或命名重构。

规则优先级如下：

1. 编译器、CMake、`.clang-format`、`.editorconfig` 等可执行配置；
2. 本规范；
3. 同一模块中已稳定存在的局部惯例。

当局部惯例与可执行配置冲突时，以可执行配置为准。

## 2. 通用规则

- 修改应保持在所属模块内；不要通过跨模块引用绕过既定依赖方向。
- 不修改 `_Generated` 文件。修改生成输入、模板或 BuildTool 后重新生成。
- 不修改 `Libraries` 中的格式、命名或实现，除非该变更明确是第三方升级/补丁。
- 新增公开 API、线程/所有权语义、反射属性或跨语言行为时，必须提供足以解释调用者责任的注释。
- 不为无关代码做批量重命名、全仓格式化或顺带重构。
- 使用现有日志、断言、异常和平台抽象；不得以标准库或平台专属调用绕开既有抽象层，除非正在扩展该抽象层。

## 3. C++

### 3.1 格式

所有一方 C++ 文件遵循根目录 `.clang-format`：C++17、4 空格缩进、120 列、左结合指针、Custom/Allman 大括号和排序后的 include。格式化只针对本次修改的一方文件。

保留模块内已有的 include 分层。新增 include 时，优先放置当前模块自身头文件，再按 Core、Runtime、Editor、其他一方模块和第三方依赖的逻辑分层；不要把模块实现依赖藏在无关的聚合头文件中。

### 3.2 命名与结构

- 类型、枚举、公开函数与公开字段使用与现有模块一致的 `PascalCase`。
- 私有实例成员使用 `m_` 前缀并保持 `PascalCase` 词干，例如 `m_Database`、`m_registeredHeaderTimestamps` 所在文件的既有命名应优先保持一致。
- 参数和局部变量使用语义明确的名称；避免单字母名称，循环索引等短生命周期变量除外。
- 一个头文件应提供清晰、最小的声明表面；实现、平台细节和昂贵 include 尽可能留在 `.cpp` 中。
- 新增平台实现必须位于既有 Platform 子层，并经公共平台抽象调用；业务模块不直接散落 Win32 或其他平台 API。

### 3.3 生命周期、错误与并发

- 明确对象所有权：裸指针仅表示既有引擎约定下的非拥有引用或受控对象地址；拥有关系使用项目已有的对象、智能指针或容器设施。
- 任何异步、任务系统或 GPU 交互代码应说明线程亲和性、提交/完成边界和资源存活要求。
- 可恢复错误使用既有日志或结果路径；仅对编程错误和不变量使用 `SE_ASSERT`。
- 不将异常、原始系统错误码或平台资源泄漏到不负责处理它们的模块边界。

## 4. 反射、生成与原生绑定

- 反射宏只放在能够被 BuildTool 稳定解析的一方声明中；宏、属性和类型名变更应视为绑定 API 变更。
- 不手工编辑 `Src/Engine/**/_Generated` 下的文件。
- 原生绑定、Box/Unbox、对象指针和封送行为变更必须同时考虑 C++ 布局、生成逻辑和 C# 声明。
- 生成的 C# 获取脚本对象原生指针时必须使用 `Object.GetUnmanagedPtr` 或项目定义的等价受控 API，不能直接读取内部指针字段。
- 修改生成器后，必须用新生成结果验证；禁止以手改生成输出掩盖生成器缺陷。

## 5. C#

### 5.1 格式与命名

Runtime 与 Editor 的一方 C# 以 `.editorconfig` 为准：使用大括号；类型、接口之外的成员和非私有字段使用 `PascalCase`；接口为 `I` + `PascalCase`；泛型参数为 `T` + `PascalCase`；私有实例字段为 `m_` + `PascalCase`；私有静态字段为 `s_` + `PascalCase`；参数和局部变量为 `camelCase`。

`_Generated` 下的 C# 被标记为 generated code，不应被人工格式化、重命名或修复。

### 5.2 托管 API 与互操作

- Runtime 和 Editor 使用 nullable reference types。新增 API 应表达真实可空性，不应以无意义的 null 抑制掩盖所有权或初始化问题。
- `unsafe`、`LibraryImport`、自定义封送和 `NativeInterop` 调用应局部化，并在 API 边界说明原生所有权、缓冲区大小、线程要求与失败行为。
- C# 不得缓存未经生命周期保证的原生指针，也不得自行复制原生对象布局。
- GUI 控件应遵循现有 Control/ContainerControl 事件与布局契约；重写输入回调时，除非有明确理由，不得吞掉基类需要处理的事件。
- 新增 Editor 功能应依赖 Runtime 的公开托管表面，不得在 Editor 中重实现 Runtime/平台/内存/渲染核心。

## 6. CMake

- 新增源文件应通过所属模块已有的 `RUNTIME_ADD`、`EDITOR_ADD` 或等价模块机制登记，不建立绕过模块聚合的临时 target。
- 新 target 必须声明最小可见性依赖；Runtime 不得依赖 Editor，Editor 不得依赖 Applications，BuildTool 不得依赖 Runtime/Editor 实现。
- 不在 CMake 中写入开发者机器绝对路径、临时生成目录或未记录的环境假设。
- C# 构建继续由根 CMake 的 `CSHARP_TARGET` 统一驱动，避免手写不一致的输出目录、配置映射或 Editor 编译符号。
- 反射参与模块必须使用 `PRECOMPILE_PROJECT`，并将可解析头文件作为生成输入。

## 7. 提交前自检

在不新增 CI 的前提下，提交者应按变更类型执行 [项目规范](项目规范.md) 的最低验证，并检查：

- 修改文件未包含 `Libraries` 或 `_Generated` 的意外人工改动；
- C++ 已按 `.clang-format` 处理，C# 未违反 `.editorconfig` 的命名和大括号规则；
- 模块依赖没有反向穿透；
- 反射/绑定/Interop 修改已重新生成；
- 构建失败若为既有基线问题，已在变更说明中与本次问题区分。
