## Observed Failure

SolarEngine source declares:

```cpp
SE_PROPERTY(API)
List<Sprite> Sprites;
```

But generated native glue currently contains:

```cpp
static int Sprites_Get(::SE::SpriteAtlas* __obj)
{
    return __obj->Sprites;
}

static void Sprites_Set(::SE::SpriteAtlas* __obj, int value)
{
    __obj->Sprites = value;
}
```

Generated C# currently contains:

```csharp
internal static partial int Internal_Sprites_Get(IntPtr __obj);
internal static partial void Internal_Sprites_Set(IntPtr __obj, int value);

public int Sprites
{
    get { return Internal_Sprites_Get(__unmanagedPtr); }
    set { Internal_Sprites_Set(__unmanagedPtr, value); }
}
```

This is invalid for a native `List<Sprite>` field. A collection should be bound through the collection ABI, resulting in managed `Sprite[]` or an equivalent array bridge, not scalar `int`.

## SolarEngine Generation Pipeline

The relevant pipeline is:

1. `ClangVisitors_Structure.cpp::VisitField`
2. API field extraction creates `ApiField`
3. `CodeGenerator_BindingsModel.cpp` turns `ApiField` into getter/setter callables
4. `CodeGenerator_BindingsCpp.cpp` emits native wrappers
5. `CodeGenerator_BindingsCSharp.cpp` emits C# P/Invoke and public property
6. `CodeGenerator_BindingsTypeMap.cpp::GetCollectionAbiInfo` decides whether a type is a collection

For the generated output to become `int`, `ApiField.cppType` has already reached the binding model as a scalar-like type, or the generator binary that produced the file did not use the collection-aware path.

The generated code is not a normal fallback from current collection mapping. In the current source, if `field.cppType` is `List<Sprite>` or `SE::List<SE::Sprite>`, `GetCollectionAbiInfo()` should classify it as `CollectionAbiKind::Variable`.

## Reflection vs API Rule Difference

Reflection fields have special handling:

- C fixed arrays are detected and marked as static arrays.
- `List<T>` is detected as a dynamic array.
- Reflection type identity is flattened from `List<T>` to `T`.
- Dynamic-array state is recorded with `PropertyFlags::IsDynamicArray`.

API binding fields need similar type-shape information. If API extraction bypasses this reflection rule and only keeps a raw or incorrectly normalized type spelling, it can diverge from reflection and generate the wrong C# binding.

The desired rule is:

- Reflection metadata should see `List<Sprite>` as element type `Sprite` plus dynamic-array flag.
- API binding should keep the binding shape as `List<Sprite>` so collection ABI can produce `Sprite[]`.
- Both paths should derive from the same resolver so they cannot drift.

## Current SolarEngine Source State

Current `ClangVisitors_Structure.cpp` already contains a unified resolver shape:

- `ResolveReflectedFieldType(...)`
- `ReflectedFieldTypeInfo::isDynamicArray`
- `ReflectedFieldTypeInfo::bindingCppType`
- API extraction assigns `field.cppType = resolvedFieldType.bindingCppType`

Current `CodeGenerator_BindingsTypeMap.cpp::GetCollectionAbiInfo(...)` also accepts collection types with `genericArgs.size() >= 1`, which is important for Flax-style containers that may carry allocator template arguments.

Therefore, if the current source is the generator that actually runs, `SpriteAtlas.Sprites` should not generate as `int`.

The mismatch between current source and generated output strongly suggests one of these is true:

1. `SpriteAtlas.typeinfo.h` and `SpriteAtlas.CSharp.cs` were generated by an older/stale BuildTool binary.
2. The BuildTool executable used for generation is not built from the current `Src/BuildTool/Code` source.
3. Generation reused stale intermediate data or stale generated files.
4. The API extraction path used by the active generator still bypasses `ResolveReflectedFieldType`.

## Flax Comparison

Flax source declares `SpriteAtlas.Sprites` as:

```cpp
API_FIELD() Array<Sprite> Sprites;
```

SolarEngine declares:

```cpp
SE_PROPERTY(API)
List<Sprite> Sprites;
```

This is a meaningful difference. Flax.Build's parser stores field types as structured `TypeInfo`:

- `TypeInfo.Type`
- `TypeInfo.GenericArgs`
- `TypeInfo.IsArray`
- `TypeInfo.ArraySize`

Flax parsing keeps `Array<Sprite>` as `Type = "Array"` plus `GenericArgs[0] = "Sprite"`.

Flax generation then treats `Array`, `Span`, and `DataContainer` specially:

- C++ native-to-managed conversion uses `MUtils::ToArray(...)`.
- Managed-to-native conversion uses `MUtils::ToArray<T>(...)` or span conversion.
- C# public type generation maps native collections to managed arrays.

Flax's `SpriteAtlas` avoids the ambiguity because it uses `Array<Sprite>`, which Flax.Build directly recognizes as a collection. SolarEngine uses `List<Sprite>`, so the Solar binding generator must explicitly include `List` in the same collection rule and must preserve the template argument through API extraction.

## Root Cause

The practical root cause is a type-shape mismatch between reflection-style field parsing and API binding field parsing.

Reflection knows that `List<Sprite>` is a dynamic array of `Sprite`. API binding generation must use that same semantic interpretation, but the generated output proves that the active generation path did not preserve `List<Sprite>` as a collection ABI type. It collapsed to scalar `int` before C++/C# wrappers were emitted.

The Flax reference confirms the intended model: collection-typed fields should remain structured collection types through parsing and only be lowered to managed arrays at binding generation time.

## Recommended Handling

No code was modified during this analysis. Recommended implementation direction:

1. Keep one shared field-type resolver for both reflection and API field extraction.
2. For `List<T>`:
   - reflection metadata: store element type `T` and `IsDynamicArray`.
   - API binding model: store binding type shape `List<T>` or fully qualified equivalent.
3. Keep collection ABI recognition namespace-aware and template-arity tolerant:
   - `Array<T>`
   - `Span<T>`
   - `List<T>`
   - `DataContainer<T>`
   - allocator variants such as `Array<T, Allocator>` or `List<T, Allocator>`
4. Ensure `GetCSharpPublicType`, `GetCSharpInteropType`, `GetInteropReturnType`, wrapper param building, and wrapper return conversion all call the same collection classifier.
5. Rebuild the BuildTool executable from the current source.
6. Delete or invalidate stale generated/intermediate binding outputs for `SpriteAtlas`.
7. Regenerate and verify expected output:

```csharp
public Sprite[] Sprites { get; set; }
```

or the project-specific fully qualified equivalent.

Native glue should use array ABI, not:

```cpp
static int Sprites_Get(...)
static void Sprites_Set(..., int value)
```

## Risk Notes

- `List<T>` in SolarEngine may have allocator/default-template behavior. The binding parser must use the first generic argument as the element type and ignore allocator arguments for managed array ABI.
- If `Sprite` requires custom struct marshalling, the element conversion must go through the same type map as normal function parameters and returns.
- If native `List<T>` ownership differs from Flax `Array<T>`, setter generation must confirm whether assigning a converted temporary list is safe or whether it should copy elements explicitly.
